## 2. Summary of findings

14 concrete spec/invariant gaps: 5 High, 8 Medium, 1 Low. The two most serious are architectural-invariant violations (checksum-after-commit, and synchronous BBolt writes from the chunk transfer loop).

## 3. Detailed findings

### F-01 [High] Checksum verification happens *after* the final file is committed — violates the atomic-commit invariant
- **Spec:** AGENTS.md §3: in-progress transfers must write to `.gofetch.part` and commit via `os.Rename` **only upon full completion and checksum verification**. PRODUCT v1: "Checksum Verification: Validates file integrity post-download via `--checksum`".
- **Evidence:** `internal/engine/coordinator.go:194-199` calls `writer.Commit()` (fsync + `os.Rename` to the final path) immediately when chunk streaming completes. Verification happens only in callers afterwards: `internal/api/handlers.go:306` then `:332-359`; `cmd/gofetch/standalone.go:180/201` then `:212-231`. On mismatch the task is marked `failed` / the CLI errors, but the corrupt file **remains at the final destination** (no rollback), and the daemon test `TestIntegration_DaemonChecksumVerification` does not check for its removal.
- **Impact:** A failed integrity check still produces a "completed" file on disk; downstream consumers can pick up bad data.

### F-02 [High] Synchronous BBolt write on the chunk-transfer hot path
- **Spec:** AGENTS.md §3 "NEVER put external DBs on the hot path… DB metrics sync strictly via async buffered channels"; DoD #3 "Zero DB queries on chunk transfer loops". T-011: "zero DB queries, zero connection locks, zero blocking I/O on the chunk transfer hot path".
- **Evidence:** `internal/engine/worker.go:253-268` calls `opts.ProgressFn(...)` after every 32 KB `WriteAt` inside the chunk read loop. The daemon's `ProgressFn` (`internal/api/handlers.go:272-304`) calls `s.persistJob(record)` at `:289-292` every 2 seconds; `persistJob` (`:58-88`) calls `state.TaskStore.SaveTask`, which executes a synchronous `db.Update` bbolt transaction (`internal/state/task_store.go:88-91`) under `jobsMu`. The off-hot-path benchmark (`bench/telemetry_bench_test.go`) only covers the Postgres/event-bus path, masking this.
- **Impact:** Real downloads block on local DB I/O from worker goroutines; contradicts the "zero DB queries on chunk loops" DoD gate.

### F-03 [High] Resume does not preserve actual transfer progress in any production entry point
- **Spec:** PRODUCT v1 "Resumability: Automatically preserves chunk state on disk to resume interrupted downloads without re-downloading completed bytes"; T-005 testable outcome; README line 12.
- **Evidence:** `DownloadWithOptions` writes a checkpoint once at partition time (`worker.go:84-94`, all `Current = Start`) and again only on error (`:141-151`, `:179-189`). `downloadChunk` advances `chunk.Current` (`:264`) but never persists it. Both daemon (`handlers.go:255`) and standalone (`standalone.go:100`) build `engine.NewCoordinator(client)` **without a checkpoint store**, so `opts.JobID` is inert: pause/resume, SIGINT, or crash re-downloads every chunk from byte 0 (the `.part` bytes are retained but ignored). `resume_test.go:105-122` manually seeds a fully populated checkpoint, so the passing test proves replay of a hand-crafted checkpoint rather than automatic state preservation. `DownloadSingleStreamWithOptions` (`coordinator.go:41-136`) never uses the store at all, so non-range downloads have no resume.
- **Impact:** The headline "resume without re-downloading" requirement is not met end-to-end.

### F-04 [High] No `--max-concurrent` / `-j` flag; configured concurrency is unused
- **Spec:** PRODUCT v1 "Concurrency Limiting: Supports global concurrency controls (`--max-concurrent` / `-j`, default: 3)"; BACKLOG T-008.
- **Evidence:** Repo-wide search finds no `--max-concurrent` or `-j` flag. `api.NewServer` hardcodes `queue.NewScheduler(3)` (`internal/api/server.go:70`). `config.Concurrency.MaxConcurrentDownloads` (default 3) is consumed only inside `config/` and its tests — never by CLI, daemon, or scheduler.
- **Impact:** Users cannot control global download concurrency as specified; the config value is a no-op.

### F-05 [High] "Sequential mode" does not implement queue-order sequential execution
- **Spec:** PRODUCT v1 "Sequential Mode: Supports strict sequential execution (`--sequential` or `-j 1`) processing items strictly in queue order"; BACKLOG T-008 testable outcome: queuing 5 URLs runs exactly 1 at a time in submitted order.
- **Evidence:** The only `--sequential` flag is on the standalone root command (`cmd/gofetch/root.go:80`, help text "Strict sequential chunk execution (FIFO)") and maps to `engine.DownloadOptions.Sequential` (`standalone.go:93`), which only orders *chunks within one file* (`worker.go:118-154`). There is no `-j 1`, no sequential option on `daemon`/`add`, and the scheduler always dispatches up to 3 concurrent tasks (`server.go:70`).
- **Note:** `tasks/T-008.md` defines "sequential" as chunk order, directly conflicting with PRODUCT.md/BACKLOG.md. Implementation follows T-008.md, not the PRD/BACKLOG.

### F-06 [Medium-High] Transient HTTP status codes (429/500/502/503/504) are not actually retried
- **Spec:** PRODUCT v1 "Error Recovery: Automatically retries failed chunks with exponential backoff"; T-005 "retry on transient network errors (… 429, 503 …)".
- **Evidence:** `internal/engine/retry.go:119` calls `IsTransient(err, 0)` — the `statusCode` parameter is never populated from real responses. `downloadChunk` (`worker.go:232-237`) converts a non-206 response into a plain `fmt.Errorf("... status %d ...")` containing no transient phrase, so `IsTransient` (`:61-82`) returns false and `ExecuteWithRetry` exits without backoff. `retry_test.go:13-38` calls `IsTransient` with explicit status codes, masking the integration gap.
- **Impact:** A server returning 503/429 mid-download fails the chunk immediately instead of retrying.

### F-07 [Medium] Per-chunk API details and GUI chunk visualizer are unimplemented
- **Spec:** T-010 "inspect chunk details"; T-016 "multi-chunk progress views / chunk visualizer"; README line 220 "Granular task metrics and chunk boundaries"; PRODUCT v1 TUI "per-chunk status".
- **Evidence:** `jobRecord.Chunks` is initialized empty (`handlers.go:135`, restored empty in `server.go:184`) and **never appended to**; `GET /api/v1/downloads/{id}` always returns `"chunks": []` (`handlers.go:459`). The web GUI renders only an overall progress bar (`app.js:212-224`) with no per-chunk view. The TUI renders per-chunk rows but labels every chunk `"▶ active"` unconditionally (`internal/ui/model.go:84-93`).
- **Impact:** Per-chunk inspection/monitoring promised in v1/v2 is absent from API, GUI, and (semantically) TUI.

### F-08 [Medium] No `If-Range` / ETag revalidation on resume
- **Spec:** BACKLOG T-005 scope: "On resume, probe server with `If-Range` / `ETag` and resume only incomplete byte ranges."
- **Evidence:** ETag is stored in the checkpoint (`worker.go:90`, `engine/checkpoint.go:11`) but no `If-Range` header is sent anywhere in the repository; `downloadChunk` sets only `Range` and `User-Agent` (`worker.go:220-221`).
- **Impact:** A resource changed mid-download can be resumed against stale bytes, producing a corrupt mixture.

### F-09 [Medium] Configuration is largely dead, and the documented schema does not match the code
- **Spec:** PRODUCT v1 "Configuration File … for default concurrency, chunk sizes, and folder mappings" and "Configurable Classification … config setting to enable, disable, or customize category mappings"; T-015.
- **Evidence:** `config.LoadConfig` is used only at `cmd/gofetch/daemon.go:31`. Of the loaded struct, only `Daemon.ListenAddr`, `Daemon.TaskDBPath`, and `Network.GlobalRateLimitBps` are applied. `MaxConcurrentDownloads`, `ChunksPerDownload`, `DefaultDownloadDir`, `AutoClassify`, `CategoryPaths`, `EnableWebGUI`, `UserAgent`, and `ConnectionTimeout` are never read outside `config/`. Classification is always enabled by default regardless of config (`handlers.go:119-124`), and custom category mappings / paths are never passed to `classifier.NewRouter` (`handlers.go:373`, `standalone.go:236`). README's YAML example (`general:`, `default_chunks_per_task`, `fsync_on_checkpoint`, `categories:` as extension lists) does not match `config.Config` (`concurrency:`, `chunks_per_download`, `storage.category_paths` as a string map); `yaml.Unmarshal` (`loader.go:91`) does not use `KnownFields`, so incorrect keys are silently ignored. `--config` exists only on `daemon`, not on root/standalone (T-015 says root/daemon).
- **Impact:** Editing config for concurrency, chunks, download dir, classification, or category paths has no effect; docs mislead users.

### F-10 [Medium] SSE progress cadence is 500 ms, not sub-100 ms
- **Spec:** PRODUCT v2 "SSE … streaming sub-100ms real-time progress"; README line 228 "sub-100ms stream"; T-014 real-time stream.
- **Evidence:** Lifecycle events are forwarded immediately, but progress frames are driven by `time.NewTicker(500 * time.Millisecond)` (`internal/api/events.go:41-60`). Consequence: the GUI's 60-sample chart (`app.js:11`, `:147-148`), labelled "Live 60s history" (`index.html:128`), actually displays about 30 seconds of data. No explicit heartbeat event is emitted (the progress frame doubles as keep-alive).
- **Impact:** Real-time dashboard latency and chart window do not match stated behaviour.

### F-11 [Medium] On-disk category folders diverge from PRODUCT.md
- **Spec:** PRODUCT v1 `Documents/`, `Video/`, `Audio/`, `Archives/`, `Software/`, **`Others/`**; BACKLOG T-006 also says `Others/` and no `Images/`.
- **Evidence:** `internal/classifier/rules.go:24-26` defines `CategoryImages = "Images"` and `CategoryMiscellaneous = "Miscellaneous"`; `Router.Route` creates exactly those directory names (`router.go:42`). The GUI labels Miscellaneous as "Others" (`index.html:114-116`), so UI and filesystem disagree. Note `tasks/T-006.md` specifies `Images/`+`Miscellaneous/`, so this is also a spec conflict.
- **Impact:** A `.bin`/unknown file lands in `Miscellaneous/`, not the documented `Others/`.

### F-12 [Medium] Integration tests do not exercise the claimed end-to-end lifecycle
- **Spec:** T-010 "full lifecycle of a download (enqueue, monitor progress, pause, resume, cancel) via the local REST API over `127.0.0.1:12701`"; T-017 "comprehensive end-to-end integration test suite".
- **Evidence:** `tests/integration/daemon_api_test.go:24-124` uses `httptest.NewRecorder` (no listener) and never starts the scheduler, so no download executes during the "lifecycle" test. `tests/integration/v2_integration_test.go` never calls `server.Start()`; step 9 (`:144-150`) writes a `urls.txt` file but never asserts anything about it. The checksum test (`:126-212`) does start the scheduler but only asserts status/error, not that the bad final file was removed (cf. F-01).
- **Impact:** The green test suite overstates verified coverage; several requirements are only smoke-tested at the handler level.

### F-13 [Medium] Per-chunk `200` responses are not safely downgraded
- **Spec:** AGENTS.md §3 "Always verify `Accept-Ranges: bytes` and status `206`; safely downgrade to single-stream download if the server returns `200`."
- **Evidence:** Downgrade occurs only at probe time (`worker.go:47-50`). If a server advertises `Accept-Ranges: bytes` but ignores a subsequent Range request, `downloadChunk:232-237` rejects the `200` response (except the artificial whole-file/single-chunk case) rather than falling back to the single-stream path.
- **Impact:** A range-supporting-but-inconsistent host fails the download instead of completing it more slowly.

### F-14 [Low] Smaller correctness/consistency issues
- `internal/engine/probe.go:183` reads header `"LastModified"` instead of `"Last-Modified"`, so `ResourceInfo.LastModified` is always empty.
- `PostgresTelemetryConsumer` (`internal/state/postgres.go`) is never instantiated by daemon/CLI and has no configuration flag to enable it; the "optional PostgreSQL consumer" exists only as a library/example.
- TUI per-chunk bars never show completion/byte-level status (`model.go:91`).
- `go.mod` requires `go 1.27.1` while AGENTS.md and the bundled toolchain tarball reference Go 1.22.

## 4. Spec inconsistencies found (not implementation defects)

1. **T-006:** `tasks/BACKLOG.md` says Milestone 2, depends on T-005, categories include `Others/` (no `Images/`); `tasks/T-006.md` says Milestone 1, depends on T-002, categories `Images/` + `Miscellaneous/`. Implementation follows the task file, not the BACKLOG/PRD.
2. **T-008:** PRODUCT.md/BACKLOG.md require queue-order sequential execution with `-j 1`; `tasks/T-008.md` redefines "sequential" as monotonic chunk order. Implementation follows the task file.
3. **README.md** advertises `-j 1` (line 18), an `Others/` folder (line 16), and a YAML schema that the `config` package does not implement (lines 181-205).

Per DoD item 4 ("Docs & Specs Updated"), these should be reconciled regardless of which behaviour is chosen as canonical.

## 6. Suggested remediation priority (not performed — read-only audit)

1. Hash the `.part` file during streaming and verify **before** `FileWriter.Commit()` (or discard/rollback on mismatch) — F-01.
2. Move `persistJob` out of `ProgressFn` into an async buffered channel/consumer — F-02.
3. Wire a checkpoint store into daemon and standalone, persist `chunk.Current` periodically, add `If-Range` revalidation, and make single-stream resumable — F-03, F-08.
4. Add `--max-concurrent`/`-j`, apply `config.Concurrency.MaxConcurrentDownloads`, and either implement queue-order sequential mode or align PRODUCT/BACKLOG with T-008.md — F-04, F-05.
5. Propagate HTTP status into retry decisions — F-06.
6. Populate `jobRecord.Chunks` and add the GUI/TUI chunk view — F-07.
7. Apply `AutoClassify`/`CategoryPaths`/download dir from config; fix README YAML and add `yaml.KnownFields(true)` — F-09, F-11.
8. Reduce SSE progress interval to <100 ms (and fix chart sampling window) — F-10.
9. Strengthen integration tests to use a real listener and started scheduler, and assert corrupt-file removal — F-12.
10. Reconcile the three spec conflicts in §4 and the README claims with the canonical behaviour.
